# 可観測性

サーバーは 2 つのポートを持ちます。`TC_PORT`（8080）がプロダクト、`TC_METRICS_ADDR`（127.0.0.1:9464）は、プロダクトではなくプロセス自身について答えるもう 1 つのリスナーです。

| パス | 答えるもの |
| --- | --- |
| `/metrics` | Prometheus テキスト形式。マッチしたルート別のリクエスト数・レイテンシヒストグラム・レスポンスサイズ、処理中リクエスト数、コネクションプールの飽和、Go ランタイム、スコープ別のレート制限拒否数、送信メールの結果別件数 |
| `/debug/pprof/*` | 稼働中プロセスの CPU・ヒープ・goroutine プロファイル |
| `/health/detail` | 依存先（DB・オブジェクトストレージ・メールリレー）ごとの詳細レポート。失敗したプローブが返したエラーを含む。503 を返すのは**必須**依存が落ちたときだけで、メールリレーが不通なだけでロードバランサから外されることはない |

## アクセス制御

リスナーは二重に守られていて、どちらの遮断も転送ヘッダを見ません。既定で loopback にバインドし、さらに直接の TCP ピアを `TC_METRICS_ALLOWED_CIDRS` と照合します。リスト外からのリクエストには 403 ではなく 404 を返します。「許可されていない」という応答は、エンドポイントが存在することを裏付けてしまうためです。

**このポートの前にリバースプロキシの設定を置かないでください。** プロキシ経由では全リクエストがプロキシのアドレスから届くので、許可エントリ 1 つでインターネット全体を通すことになります。

`compose.prod.yml` はホストの `127.0.0.1:9464` に公開します。同じ compose ネットワーク上のスクレイパからは `api:9464` で到達できます。

```bash
curl -s 127.0.0.1:9464/metrics | head
curl -s 127.0.0.1:9464/health/detail | jq
go tool pprof http://127.0.0.1:9464/debug/pprof/profile?seconds=30
```

公開側の `/health` は、ロードバランサが必要とするものだけを返します。軽く、認証不要で、どの依存先が不調かは伝えません。

## アクセスログ

アクセスログは URL ではなくルートを記録します。共有トークンはパスの一部で、パスワード再設定はトークンをクエリに載せます。一般的なアクセスログでは、最も長く保存され最も広く読まれる場所に、有効な資格情報を書き残すことになります。

各行に載るのは、マッチしたルートパターン・ステータス・所要時間・レスポンスサイズ・クライアント IP・リクエスト識別子です。識別子は `X-Request-Id` として返り、そのリクエストが出す他のすべてのログ行にも付くので、1 つの値で一連の流れを拾えます。呼び出し側が指定した識別子を採用するのは、`TC_TRUSTED_PROXIES` に載っているホップからのときだけです。

web サービスの nginx も同じ規則に従います。アクセスログに載るのはクエリ文字列を除いたパスだけで、`/share/`・`/embed/`・`/invites/` の URL はトークンの区間を置き換え、`Referer` は記録しません。失敗時にだけ書かれるエラーログには、失敗したリクエストのリクエスト行と `Referer` がそのまま載ります。
